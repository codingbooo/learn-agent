上下文窗口的物理本质与 KV 缓存机制

建议阅读时长：8 分钟 | 架构师心智模型篇

一、上下文（Context）是 Agent 的易失性 RAM

做 Android 开发，你一定对内存敏感：RAM 空间有限，对象常驻容易 OOM，进程被杀前需要持久化。

在 Agent 系统里：Context Window（上下文窗口）就是大模型的物理 RAM。所有给大模型看的系统提示词、工具定义、历史聊天、工具返回结果，都必须塞进这个“内存窗口”中。

但它有两大反直觉的物理特性：

  • 无状态性（Stateless）：大模型服务端本身不保存你上一秒的对话。每一次你发消息，客户端必须把全部历史 Token 从头到尾重新发一次。
  • 二次方注意力开销（O(N²) Complexity）：上下文不是无限塞的。随着 Token 数量翻倍，注意力的计算开销和内存占用呈平方级暴增。
Android 架构师类比
如果把调用 LLM 比作启动一个组件：它不是常驻的 Service，而是每次请求都被彻底杀掉后重建的 Activity。每次渲染画面，你都必须把整个 savedInstanceState Bundle 完整重新反序列化一遍。

二、Prompt Caching（KV 缓存）：拯救成本与延迟的银弹

既然每次都要重发整个历史，为什么现在的 Agent（如 Claude Code / Cursor）反应越来越快，费用反而下降了 90%？核心技术就是 KV Cache（键值缓存）。

大模型处理文本分为两阶段：Prefill（预填充计算） 和 Decode（逐字解码）。预填充阶段计算出的注意力矩阵，可以保存在显存中复用。

三、架构师必背：破坏 Cache 的“致命禁忌”

KV Cache 依赖严格的前缀哈希匹配（Prefix Matching）。只要前缀发生哪怕 1 个字节的变动，后面的缓存全部失效！

操作方式 Cache 状态 架构后果
在上下文末尾追加新消息 ✅ 命中前缀 享受极速响应与 1 折推理成本
动态在 System Prompt 插入实时时间戳 ❌ 彻底失效 每次请求前缀都不同，缓存命中率 0%
对话中途动态修改/增删 Tools 工具定义 ❌ 彻底失效 工具描述在前置位置，破坏整体前缀 Hash

今日 1 分钟架构底线（Takeaway）

  1. 上下文即 RAM：它是昂贵的易失性资源，不能无休止往里堆积未提炼的日志。
  2. 前缀稳定性神圣不可侵犯：系统级 Prompt、技能声明、工具 Schema 必须固化在头部，绝对不要在会话中途动态变更。
