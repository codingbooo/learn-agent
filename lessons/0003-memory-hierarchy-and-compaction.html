记忆系统的多级分层与冷热数据置换

建议阅读时长：8 分钟 | 架构师心智模型篇

一、直觉陷阱：以为“向量数据库(Vector DB)”能包打一切

很多技术方案一谈到 Agent 长期记忆，第一反应就是：把用户所有对话切片，存进向量数据库，每次提问做 Cosine 相似度检索。

在实际工业落地中，纯语义向量检索的召回率经常翻车。比如用户问：“我上周二改的那个 build.gradle 文件路径在哪？”，向量数据库往往会召回一堆关于“Gradle 插件开发”的泛义文章，反而漏掉精准的路径。

优秀的 Agent 架构从不依赖单一存储，而是像操作系统一样，设计严格的多级存储金字塔（Storage Hierarchy）。

Android 架构师类比
Agent 记忆系统完全对标 Android 的存储拓扑：Context 窗口 = RAM（快且贵，进程重启清空）；持久化 Memory = Room/SQLite（结构化精准存储）；长尾历史 = 磁盘文件/网络云端（冷数据，按需分页换入）。

三、冷热置换：Context 压缩（Compaction）机制

当多轮交互导致 L1 工作内存接近上限时，系统必须触发垃圾回收与分页置换，这就是“上下文压缩（Context Compaction）”：

    autonumber
    participant Agent as 🤖 Agent 运行器
    participant LLM as 🧠 压缩专用模型
    participant DB as 💾 持久化状态库 (SQLite)

    Agent->>DB: 1. 全量完整快照归档持久化 (保留审计链)
    Agent->>LLM: 2. 提交前 50 轮历史: "提取核心决策与状态"
    LLM-->>Agent: 3. 输出提炼摘要 (从 50K 压缩至 1K Tokens)
    Note over Agent: 4. 丢弃原始冗余工具输出，仅保留核心摘要 + 最近 5 轮交互
    Note over Agent: 上下文水位回落至 20%，继续无缝响应

今日 1 分钟架构底线（Takeaway）

  1. 不要迷信纯语义向量：工程落地中，结构化元数据（时间、标签）+ 倒排索引全文检索（FTS5/BM25）的准确度远胜暴力向量相似度。
  2. 分层治理是唯一正道：短期工作记忆靠压缩归纳，长期静态事实靠独立配置，历史冷数据靠检索拉取。

思考题：当用户要求 Agent 排查线上日志中的 NullPointerException at PaymentActivity.kt:142 时，为什么暴力向量检索（Embedding Similarity）往往召回一堆通用异常文档，而传统的全文检索（FTS5）能秒级命中？

架构解析：
向量检索依赖模糊语义共现，像类名、行号、UUID 这类极具区分度的“硬关键字（Keyword Token）”在高维语义空间中会被稀释；而全文倒排索引（FTS5 / BM25）是精确字面频次与词元倒排，对唯一标识符和报错行号具有 100% 精准召回率。
工业级混合解法：先走 BM25/FTS5 过滤精确命中集，再辅以向量做语义重排（Rerank）。
