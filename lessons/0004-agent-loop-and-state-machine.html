Agent 运行循环与状态机 —— 拆解 ReAct Loop 的工程本质

建议阅读时长：8 分钟 | 运行时控制流篇

一、破除神秘感：Agent 不是活体生物，是有限状态机

很多技术宣传常将 AI Agent 拟人化为“能自主思考行动的数字打工人”。从系统架构师的视角看，这种拟人化极具误导性。

工业级 Agent 的物理本质，仅仅是一个由外部宿主进程驱动的 Event Loop（事件循环）驱动的有限状态机（FSM）。大语言模型本身没有任何自主意识，它既不会主动触发时钟中断，也不会主动拉起后台线程；它只是一个被宿主程序一次次轮询调用的“下一跳状态决策函数”。

Android 架构师类比
Agent 运行时完全对标 Android 主线程的消息泵：LLM 是无状态的业务解码器；Agent Runtime 是 Looper；会话上下文数组是 MessageQueue。Looper 从队列取出历史上下文投递给模型，模型返回 Tool Call 相当于发送了一个带回调的 Message / Runnable。宿主执行完毕后将结果封装为 Observation 重新 enqueueMessage()，驱动下一次 loop() 迭代。

二、ReAct 范式的状态转移拓扑

工业界最主流的 Agent 执行闭环是 ReAct（Reasoning + Acting） 模式。宿主程序与模型之间通过严格的状态转移闭环协同运行：

stateDiagram-v2
    [*] --> Idle: 等待输入
    Idle --> Reasoning: 用户发出 Prompt
    
    state Reasoning {
        [*] --> ContextPacking: 拼接历史与 Tool 声明
        ContextPacking --> ModelInfer: LLM 前向推理采样
    }

    ModelInfer --> Finished: 输出普通文本 (终态回答)
    ModelInfer --> Acting: 输出结构化 Tool Call
    
    state Acting {
        ValidateSchema --> HostExec: 沙箱或 OS 执行工具
        HostExec --> Observe: 捕获 stdout/stderr 结果
    }

    Acting --> Reasoning: 组装 Observation 追加至上下文
    Finished --> [*]: 渲染响应并等待下次唤醒

三、架构师视角：工业级运行时必须治理的工程陷阱

在 Demo 级别编写一个 while True: step() 的 Agent 循环只需十行代码，但在生产级长链任务中，宿主运行时必须部署三道确定性防线：

🚨 1. 死循环熔断（Action Loop Detection）

当工具执行持续报错（如文件不存在）时，概率模型极易陷入“重试-报错-原样重试”的死锁循环。成熟的 Runtime 必须维护滑动窗口（Sliding Window），计算最近 N 次 Tool Call 签名的相似度；一旦检测到重复调用，必须由宿主硬性注入中断信号或 Steering 指令，强行跳出死循环。

⚠️ 2. 上下文膨胀与污染隔离（Result Truncation）

工具执行结果（如抓取到的网页 HTML 或超大堆栈日志）可能高达数百 KB。如果直接完整推入 MessageQueue，会导致单轮迭代消耗数万 Tokens，甚至直接挤爆 Context Window。宿主层必须具备流式截断、头尾保留（Head-Tail Truncation）以及落盘分页机制。

🛡️ 3. 宿主主控权不移交（Host In Control）

无论模型多聪明，它永远只是系统的“策略建议者”。底层的系统权限隔离、工具调用的并发控制、环境读写权限审批，必须牢牢掌控在宿主容器手中。不可逆的高危操作（如删除库表、向外发送敏感数据）必须有宿主 Interceptor 拦截机制。

今日 1 分钟架构底线（Takeaway）

  1. 主控权在宿主，不在模型：Agent 的外壳是确定性的事件循环状态机，LLM 只负责状态转移函数中的意图推断。不要期望模型自发控制节奏，节奏完全由宿主调度器掌控。
  2. 生产级可靠性取决于防御性外壳：衡量一个 Agent 架构成熟度的标准，不是它的 Prompt 辞藻有多华丽，而是它的步数熔断、循环检测、上下文截断与异常自愈机制有多健壮。

参考架构实践：错误反馈闭环（Error Feedback Loop）与阶梯降级
1. 错误转化为 Observation：宿主绝不能直接 crash 进程，而是将工具的标准错误（stderr/Exception stack）格式化为结构化的 Observation 消息，重新塞回 MessageQueue，让 LLM 看到自己调用失败的具体原因（利用自回归能力自我修复）。
2. 步数配额与干预（Steering）：设置重试配额（如连续失败 3 次）。达到阈值后，宿主主动注入一条系统级 Steering 提示：“该工具当前不可用，请更换排查策略或降级回答”。
3. 保底兜底（Safe Fallback）：达到最大步数上限后强制中断循环，向终端用户坦诚输出部分已完成事实与阻断瓶颈，保持系统的可预测性与健壮性。
