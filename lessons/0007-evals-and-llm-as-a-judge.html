一、传统断言失效：概率系统的“测试困境”

在经典软件工程中，测试的核心基石是确定性断言：assertEquals(expected, actual)。只要输入恒定，内部逻辑执行后输出必然严格一致。

然而进入 Agent 时代，系统的核心计算单元是自回归概率模型。即使设置 Temperature 为 0，由于浮点精度微抖或上下文动态差异，模型每次输出的自然语言句式、代码变量名乃至调用工具的微观次序都可能发生漂移。团队通常会经历三个阶段的惨痛教训：

  • 肉眼抽检（Vibe Check）：开发者改完一段 System Prompt，在聊天窗口随意试了 3 个 Case，感觉效果不错便直接发布，随后在线上遭遇客诉雪崩；
  • 打地鼠效应（Whack-a-Mole）：为了修补线上某个特定 Bad Case，开发者在 Prompt 里硬编码补充规则，结果导致另外十个原本正常的场景发生隐蔽回归（Regression）；
  • 字符串硬匹配失效：尝试用正则校验模型输出，一旦模型换个同义词或微调换行符，测试流水线大面积误报飘红。
Android 架构师类比
给 Agent 写测试，就如同给多机型碎片化时代的 Android ROM 做系统级验收：
1. 无法用简单单元测试覆盖：你不可能用单个 JUnit 断言去验证一台第三方手机的触控动画是否“流畅跟手”；
2. Android CTS（兼容性测试套件）：Google 解决机型碎片化的终极手段不是审查厂商驱动源码，而是建立 CTS 黑盒测试套件——只定义输入事件与最终状态验收边界，任何厂商 ROM 必须通过数十万条 CTS 测试用例才获准出厂；
3. Evals 就是 Agent 领域的 CTS：在 Agent 工程中，Prompt、模型版本与工具定义都是可变的“驱动实现”，唯有标准化的 Evals 测试集 才是系统行为的不可变契约。

三、LLM-as-a-Judge 的架构防线与校准

让高阶模型（如 GPT-4 / Claude 3.5 Sonnet）来评判待测 Agent 的输出，已成为业界标配。但裁判模型本身同样是概率机，架构师必须消除其内生的认知偏差：

⚖️ 1. 结构化打分准则（Rubric-based Scoring）

绝不能让裁判模型泛泛地“打 1~10 分”！模型对笼统分数缺乏稳定尺度。必须提供极度详尽的打分量表（Rubrics）。例如评估代码解释：“1 分：存在事实性错误；3 分：逻辑正确但遗漏边界条件；5 分：完全正确且给出时间复杂度分析与防护建议”。打分输出必须强制包裹在 JSON Schema 中，且要求先输出推理证据（Chain-of-Thought），再输出量化分值。

🔄 2. 位置偏差与配对乱序消解（Position Bias Mitigation）

在做 Pairwise（两两对比 A/B 测）时，裁判模型普遍存在严重的位置偏见（默认倾向于选择 Candidate 1 或 Candidate 2）。工业级评测框架必须执行双向对调评测：将样本 (A, B) 和 (B, A) 分别输入裁判，仅当两次裁决结论完全对称时才判定有效，不一致时标记为平局或分歧。

🚦 3. Eval-Driven Development（EDD 评测驱动开发）

如同传统重构遵循 TDD（测试驱动开发），在 Agent 开发中必须践行 EDD（Eval-Driven Development）：在修改任何 Prompt、升级基础模型或新增工具前，先向 Eval 数据集中沉淀至少 50~100 个历史 Bad Case 与 Golden 标准样本；将 Evals 接入 GitHub Actions / CI 流水线，任何 MR/PR 只有在综合评分与通过率不发生 Regression 的前提下，才允许合并上线。

今日 1 分钟架构底线（Takeaway）

  1. 没有 Evals 的 Agent 是无法维护的玩具：纯靠肉眼试跑是工程灾难的起点。只有建立覆盖全面、自动跑批的 Evals 数据集，团队才敢放心迭代 Prompt 和切换底座模型。
  2. 分层验收与硬指标兜底：金字塔底层用确定性断言（Schema、Lint、AST）阻断物理错误，中层用高阶模型裁判（Rubric + 消除偏差）对齐语义，顶层用真实执行（沙箱回归）衡量端到端任务达成。
🎯 架构师课后微测验

思考题：你的团队准备将线上生产环境的核心 Agent 底座从昂贵的“超大闭源模型”降级切换为低成本的“自部署开源开源蒸馏模型”。为了确保线上质量不下滑，负责的工程师提议：“我们写一个脚本，把两千条线上日志分别跑一遍，如果两者文本相似度（如 BLEU 或 Embedding 距离）达到 90% 以上就可以切流”。这种验收方案存在什么致命架构漏洞？作为架构师应如何设计正确的迁移验收流水线？

🔍 点击展开：架构解析与参考答案
参考架构实践：从“表面文本相似”到“状态机与行为达成（Goal Completion）”验证
1. 文本相似度度量的致命缺陷：高文本相似度完全不等于逻辑等价。例如对于一段支付 SQL，只要表名、字段名或 WHERE status = 1 漏写一个条件，BLEU 相似度依然高达 98%，但在生产环境中会直接酿成灾难性线上资损；反之，模型给出更优雅但完全不同的解法，文本相似度可能极低却完全正确。
2. 正确的模型迁移验收体系（Golden Dataset + Evals）：
• 工具调用行为保真度（Action Matching）：校验小模型在面对复杂意图时，生成的 tool_calls 名称、参数 Schema 准确率是否与大模型基线一致；
• 沙箱端到端执行结果比对（Execution-based Evals）：在隔离沙箱中执行 Agent 操作，直接断言其对环境产生的状态变更（如数据库变更行数、最终输出文件的哈希或单测结果）；
• Rubric-based LLM-as-a-Judge 盲测（Double-Blind Evaluation）：用超大模型作为第三方裁判，打乱顺序盲审小模型与大模型的输出，统计 Win/Tie/Loss 胜率，确认在核心业务维度上没有显著退化。
