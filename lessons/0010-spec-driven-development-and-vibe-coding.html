篇章 4 · Vibe Coding 工程范式 · 第 10 讲

规格驱动开发（Spec-Driven Development） —— 终结随意编码的 Vibe Coding 架构工程

建议阅读时长：8~10 分钟 | 研发架构进化篇

一、自然语言编程的幻觉：从 Prompt-and-Pray 到架构崩塌

近年来，“Vibe Coding”被大众广泛解读为“完全靠感觉和自然语言对话写代码”。开发者在 IDE 侧边栏对大模型随手输入一段模糊需求：“帮我写一个用户会员结算模块”，模型便迅速吐出几百行代码。

这种纯靠直觉的 Prompt-and-Pray 模式在独立玩具项目或百行脚本中令人惊叹，但一旦进入百万行级企业代码库，就会迅速引发灾难性的“架构熵增雪崩”：

  • 架构规范漂移（Architecture Drift）：系统本采用严苛的单向数据流 MVI 架构，Agent 却在生成的代码中随意引入全局 EventBus、单例回调或混用旧版三方库；
  • 隐性边界缺失（Implicit Blind Spots）：自然语言充满歧义与漏洞。模型自作主张忽略了网络断连重试、并发幂等校验、敏感信息脱敏与内存泄露防护；
  • 打地鼠式改动（Context Fragmentation）：修完 A 模块的 Bug，Agent 顺手重构了公共接口，导致依赖它的 B 和 C 模块产生大面积隐蔽编译崩溃。

大模型极擅长补全语法实现，但极不擅长在无约束状态下“猜透系统隐性契约”。真正的现代 Vibe Coding，绝非散漫的聊天，而是高度结构化的规格驱动开发（Spec-Driven Development, SDD）。

Android 架构师类比
给 Agent 随意派发聊天指令，就如同在大型 Android App 团队中，让实习生完全不看方案设计与接口定义，凭口头一句话直接去主工程里改 BaseActivity 和核心网络库。

成熟的 Android 架构流程从来都是：
1. 技术方案评审（Technical Design Review）：在写第一行业务逻辑前，主架构师必须先产出详细方案设计文档（TDD），冻结模块依赖拓扑与线程调度契约；
2. 契约先行（Contract First）：通过 AIDL / Protocol Buffers 严格固化跨进程通信数据结构，通过 Kotlin sealed interface 固化 UI State 与 User Intent；
3. SDD 体系下的角色跃迁：架构师的角色从“体力型码农（实现者）”升级为“系统规格审核官（Spec Author & Gatekeeper）”；而 Agent 则充当“超高并发的 Junior 工程师与快速编译器”。代码不是随意长出来的，而是被 Spec 严格投影约束出来的！

二、工业级 SDD 四层规格栈架构（The 4-Layer Spec Stack）

三种软件生产范式的系统性工程对比：

工程维度 自由聊天式编码 (Prompt & Pray) 传统人工编码 (Manual TDD) 规格驱动开发 (Spec-Driven Agentic)
输入形态 模糊口头需求、零散问答 人工阅读 PRD，自行构思代码 结构化 Markdown Spec + 强类型契约

三、SDD 落地核心心智：将 Spec 视为可编译的“第一等公民”

很多工程团队误以为写 Spec 会拖慢开发节奏。但在 Agent 时代，Spec 的物理性质已经发生了根本性改变：

📝 1. Spec 从“给人看的文档”转变为“给模型执行的 AST”

过去的技术方案文档往往写完就躺在 Wiki 里发霉，实现代码与文档逐渐脱节。在 SDD 中，Spec 是一套机器可读的工程中间表征（IR）。它通过项目根目录的 .cursorrules、CLAUDE.md 或分层 specs/feature-xxx.md 直接作为 Agent 运行时不可越过的 System Invariant 载入，模型生成逻辑时逐条将其当作编译约束。

🔄 2. 先“对话生成 Spec”，再“冻结 Spec 生成代码”的两阶段架构

绝不要在同一个 Prompt 链路中让模型同时做“方案设计”和“写全部代码”！
• 第一阶段（架构推演）：向 Agent 描述业务目标，要求其仅输出技术选型、接口定义、潜在异常点与用例清单（Spec Draft）。人类在此阶段重点审查边缘条件与架构选型；
• 第二阶段（确定性投射）：Spec 经人类确认并冻结后，以只读形式传入执行 Agent，触发并发代码实现与单元测试生成。两阶段分离将模型的幻觉率降低了一个数量级。

🛡️ 3. 编译器与单测形成的“确定性反馈闭环”（Loop with Proof）

传统写完代码需要人工肉眼核对。在 SDD 闭环中，人类编写的 Spec 明确定义了验收基准。Agent 输出 Patch 后，系统自动触发 gradle test / eslint / 静态类型推断。如果类型报错，Agent 仅凭编译器的错误堆栈在有限上下文内自愈修复，无需人类介入纠错。

今日 1 分钟架构底线（Takeaway）

  1. 代码只是 Spec 的副产物：在 Agentic 时代，代码库的可维护性取决于 Spec 的严谨度。严谨的 Spec 可以随时一键重生成不同语言实现，但缺少 Spec 的代码堆叠就是技术债务的死胡同。
  2. 先对齐认知边界，再启动代码发射：推行“推演 Spec → 冻结契约 → 代理编码 → 编译器门禁”的标准流水线，将架构师从繁重低效的聊天纠错中解脱出来，真正发挥高阶抽象决策价值。
🎯 架构师课后微测验

思考题：某团队在 Android 项目中引入了 AI 编码助手，团队工程师习惯通过对话“指导”Agent 连续修改了 8 个核心 Presenter 文件。虽然本地看起来功能正常，但在后续合入主干后，由于隐藏的多线程竞态与全局上下文泄露，引发了严重的线上崩溃率上涨。如果你是该项目的主架构师，在引入 SDD（规格驱动开发）理念后，你会制定怎样的流水线规范与目录契约来彻底预防该问题？

🔍 点击展开：架构解析与参考答案
参考架构实践：构筑三层 SDD 研发闭环门禁
1. 定义不可侵犯的 ADR 规则文件（如项目根目录 CLAUDE.md / .cursorrules）：
• 显式声明全局架构不变量：如“严禁在 ViewModel/Presenter 中直接引用 Context”、“所有异步调度必须绑定 viewModelScope，严禁裸起 Thread / GlobalScope”；
• 显式定义模块依赖图与只读路径：核心公共基础设施目录设为 Agent 只读，防止 Agent 私自窜改底层基础接口；
2. 推行“两阶段 PR 审查”规范：
• 阶段一（Spec PR）：任何 Feature 开发必须先提交一份包含接口契约、时序图与验收测试用例的 Markdown 规格文件，由资深架构师评审通过后方可打上 spec-approved 标签；
• 阶段二（Implementation PR）：Agent 基于已通过的 Spec 单独生成代码变更，且必须附带针对该 Spec 验收标准的自动化测试；
3. CI 物理流水线硬阻断：
• 接入静态分析工具（如 Android Lint 针对内存泄露的自定义规则、Detekt 架构规则检查）；
• 只要 Agent 生成的代码违反了预设的线程调度规则或存在 Context 泄露隐患，CI 编译期直接红牌阻断，阻止劣质生成物渗透进主干分支。
