三、实战架构评审题（Capstone Dilemma）

🚨 场景评审：突发性能与成本危机

业务背景：团队上线了一个“线上故障自主排查 Agent”。运营一周后，财务发出预警：API Token 消耗是预期的 12 倍；同时客服反馈高频对话到达第 20 轮之后，Agent 经常开始胡言乱语、报错丢失前置上下文。

技术排查发现以下 3 个实现细节，请指出其设计缺陷：

  1. 为了让 Agent 知道当前时间，在 System Prompt 开头注入了 当前时间: yyyy-MM-dd HH:mm:ss；
  2. 为了让 Agent 能查日志，写了一个包含 30 种日志检索过滤参数的巨型 Tool，并在每轮交互中把上一次检索到的 5000 行原始 Log 完整塞入历史；
  3. 未实现任何记忆分层机制，所有历史会话直接无限向后拼接直到触发 128k 窗口硬上限。
🔍 点击展开：架构师级整改方案

整改方案 1（拯救成本与延迟）：将动态时间戳从 System Prompt 剥离，固定头部 System Prompt 与工具 Schema；时间戳下沉到用户单次消息或封装为工具。收益：KV Cache 命中率从 0% 跃升至 85%+，费用立降 80%。

整改方案 2（治理上下文污染）：宿主端建立日志过滤中间件，不要把 5000 行未清洗 Log 灌进上下文。强制通过本地 SQLite/FTS5 过滤，仅将前 5 条关键 StackTrace 注入 LLM。收益：避免注意力被噪音淹没，大幅提升诊断准度。

整改方案 3（垃圾回收与状态持久化）：设立上下文容量水位线（如 70%）。达到阈值后自动触发 Compaction：将历史交互全量冷备份到 SQLite，调用轻量模型归纳出关键排查进展摘要，上下文降回 20% 水位继续运行。收益：彻底根除 20 轮后的幻觉与上下文爆仓崩溃。
