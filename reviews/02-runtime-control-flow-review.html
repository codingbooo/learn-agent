三、实战架构评审题：长链路自动化系统的失控灾难

🚨 场景评审：千万级代码仓自动化迁移 Agent

业务背景：某团队设计了一个“Android 模块自动迁移 KMP（Kotlin Multiplatform）”的 Agent 系统。在实际运行第 15 分钟时，系统耗尽了 500 万 Token，产生死循环，并在 Git 仓库提交了包含大量编译报错的未完成代码。

架构师调取执行轨迹后发现 3 处致命缺陷，请指出其背后的系统性成因：

  1. 单一上下文平铺：让一个单体 Agent 负责整个模块的源码扫描、依赖解析、代码转换与单测执行，所有 git diff 和 gradle 输出直接灌入上下文；
  2. 工具权限裸奔：直接向 Agent 开放了带 sudo 权限的宿主 Shell 工具，且未对外部网络出站进行限制；
  3. 贪心无契约并发：拆分子任务时，并发唤醒了 5 个 Coder 子代理各自修改紧密耦合的接口，没有先做契约冻结。
🔍 点击展开：架构师级根治重构方案

重构方案 1（治理上下文稀释）：引入 Hierarchical Sub-agent 架构。主调度器只保存模块依赖图；源码检索与代码翻译分别在独立的子代理中运行，中间产物持久化到磁盘，只向父代理汇报 TaskResult(status, modified_files) 句柄。根除注意力稀释与 Token 爆炸。

重构方案 2（建立特权沙箱边界）：Shell 执行环境迁移至隔离 Docker 容器，挂载只读工作区副本；破坏性命令（git push、外部网络访问）引入人在回路（HITL）审批和白名单路由。阻断供应链攻击与不可逆破坏。

重构方案 3（契约优先与静态编译门禁）：在派发并发迁移任务前，主代理必须先定义并冻结公共 API 接口；子代理提交后，系统必须调用确定性构建工具（./gradlew check）进行自动化编译验证，编译失败触发局部带回退重试，而不是放任幻觉入库。
