三、实战架构评审题：万行旧工程引入 AI 编码导致的“架构腐化与幽灵 Bug”

🚨 场景评审：千万级日活 App 团队的 Vibe Coding 翻车事故

业务背景：某移动端团队为了提高人效，全员引入了最新款 AI 编程助手开展“自由 Vibe Coding”。两个月后团队发现交付速度不但没有提升，反而陷入崩溃：

  1. 隐蔽幽灵 Bug 激增：AI 在修改老旧复杂业务逻辑时，因为全量写盘或粗暴匹配，不经意删除了原函数中用于低端机保活与异常兼容的边缘分支（如 try-catch 特殊补丁），上线后 Crash 率剧增；
  2. 架构分层彻底击穿：原本严格遵循 MVI 单向数据流与 Repository 模式的架构，被 AI 在 Activity / ViewModel 中随意滥用直接注入数据库 DAO、单例甚至网络 Client，代码腐化成“意大利面条”；
  3. 长耗时构建拖垮开发心流：团队将每次代码修改都挂载在 CI 的完整全量构建流水线上（耗时 15 分钟），AI 遇到微小拼写错误反复自愈尝试，导致开发者电脑整天处于风扇狂转的卡顿等待中。

请以资深系统架构师视角，结合篇章 4 所学的 SDD 规格栈、AST 索引与编译器分级自愈架构，给出成体系的底层治理方案。

🔍 点击展开：架构师级治理重构方案

治理方案 1（以 Spec 冻结架构不变量，阻断架构腐化）：
• 确立不可侵犯的 L1 架构不变量：在项目工程中确立架构守则并在 Agent 系统 Prompt 中建立强约束（例如：“ViewModel 严禁持有 Context，严禁直接引用 Room DAO；必须通过 UseCase 暴露的 Flow/LiveData 交互”）；
• 推行 ArchUnit / 自研静态架构规则门禁：在编译期通过字节码静态分析检测包依赖违规（如 Presentation 层引用 Data 层内部实现），一旦违规在 2 秒内直接阻断，从物理层面禁止“随缘调用”。

治理方案 2（细粒度 Search/Replace 补丁与关键防护注释）：
• 强制使用细粒度差异补丁引擎：严禁 AI 工具对超过 200 行的文件进行全量重写，一律采用基于 AST 或搜索块替换的差异合并；
• 关键防御性代码标记保护：对涉及厂商兼容性、保活反射的脆弱代码段包裹特殊注解（如 @CriticalArchGuard("Do not modify without review")），补丁引擎检测到试图修改该受保护区域时强制告警或阻断。

治理方案 3（分级构建与增量快速反馈流水线）：
• 解耦自愈校验门禁：自愈循环绝对不能触发全量打包（15分钟），必须设计“分级加速金字塔”：
  1. L1 秒级门禁（0~2秒）：文件保存时仅触发单个源文件的语法检查（ktlint + 抽象语法树校验）；
  2. L2 模块级门禁（5~10秒）：基于 Gradle 增量编译任务（compileDebugKotlin --dry-run / incremental）仅编译修改所在的单个 subproject；
  3. L3 契约测试门禁（15~30秒）：仅运行该模块对应的 JVM 本地单元测试；
• 只有当 L1~L3 快速自愈闭环全部通过并提交 Git 后，才交由后台异步 CI 执行全量集成打包，兼顾极限开发心流与系统级质量基线。
